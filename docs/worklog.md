## 2026-10-15 识别栈小程序适配 + 公共牌堆/罚分条误读修复

用户反馈：公共牌堆经常读错、罚分符（先手标记）易读错、走子动画会被读成半成品。

   行区/墙/工厂/面板全读对——**不需要重标定**（手机截图 ≠ 小程序窗口，以小程序为准）。
2. **罚分条标记漏计**（`read_floor`）：先手标记砖（白底黑"1"）饱和度低被
   `FILLED_SAT` 滤掉 → 占用数少 1、先手归属丢失。补"白底+暗字形"判据，
   并用**暗像素饱和度**区分标记（纯黑无彩色 dark_sat≈0.2）与白砖（青色花纹 dark_sat≈0.6）。
   状态新增 `floor_token`（标记在谁的罚分条上 = 谁下轮先手）、`floor_colours` 中标记记 None（不占花色）。
3. **公共牌堆误读三连修**（实测 blob 统计钉死）：
   - "X"字形/数字墨迹形成独立 blob（fill 0.53~0.57 vs 行图标 0.98），
     aspect 过滤挡不住 → **填充率过滤**（>0.72 才算行）；

## 2026-10-15 「AI 乱走」事故：建议输出层编码映射 bug（模型无辜）

实机对局发现 AI 乱走。隔离测试（手工构造确定正确局面喂 `azul suggest`，绕开识别）定位：

- **症状**：三个场景的概率全均匀（9.1%/8.3% = 1/合法着法数），top-1 = 合法列表第一个。
- **根因**（`azul-cli/src/suggest.rs`）：MCTS 的 `policy` 按**引擎 180 编码**
  （`azul_az::to_index`：src=0..4 工厂/5=中央）索引，但查询用了**garden 编码**
  （g=0 中央/1..5 圆盘）下标 —— 两套是置换关系，查错全是 0 → 全被 `>0` 过滤 →
  落到均匀概率兜底 → top-1 随机。**模型与识别都没问题**。
- **修复**：`policy[azul_az::to_index(&m)]`。修复后隔离测试三场景全过（概率正常分化：
  85.6%/84.6% 集中在正确着法）。对局侧 duel.rs 一直用 to_index，训练/验收不受影响。
- **防回归**：新增 `garden_and_engine_index_are_consistent_permutation` 测试
  （校验两套编码是双射，杜绝再次混用）。

教训：**两套 180 动作编码并存是高危陷阱**，任何"数组按 A 索引、下标按 B"都会静默出错；
凡跨编码查表必须先显式转换。

## 2026-10-16 「莫名罚分 / 瞎走」事故：识别-引擎集成四个叠加 bug（模型无辜）

实机反馈"AI 瞎走、莫名让我罚分"。逐层隔离定位到 **4 个集成 bug**（模型/权重无辜）：

1. **工厂盘读数 = 像素个数而非砖数**（`azread/reader.py::_read_discs`）：
   旧实现统计盘内采样像素，一盘报 12~36 张砖（真值最多 4 张）。引擎以为一摞
   10 张蓝砖，一拿多余全溢出进罚分条 —— **"莫名罚分"直接来源**。
   修复：每盘 2×2 槽位逐槽判空（tileish 阈值 0.25，实测空槽 0.00/满槽 ≥0.69）
   + `_classify_tile` 判色，数**砖数**。state 侧加 ≤4 截断防呆。
2. **盘序错位**：azread 输出 [左上,左下,右上,右下,中间]，引擎/面板按
   [左上,右上,中间,左下,右下] 命名 → 建议"从右上盘拿"实际指左下盘。
   修复：DISCS 重排为与引擎/面板 1:1 同序。
3. **墙色位错位**（`azul-core/src/garden.rs::to_slow_state`）：`mask |= 1 << c`
   把**列号当色号**，但格位 (r,c) 的墙色是 `(c-r)%5`，行 1~4 全错位 → 引擎以为
   某色位空着、实际墙位已占，砖放不进只能进罚分条。
   修复：`1 << wall_colour(r, c)`。防回归测试 `garden_wall_cells_map_to_colour_bits`。
4. **搜索视角错位**（`azul-cli/src/suggest.rs::run`）：`to_slow_state` 把 turn 设成
   `next_player`（局面该走的人），但 suggest 是"替 who 算建议"，轮对方走时引擎就
   以**对方视角**搜索、生成对方的合法着法（"拿黑→第3行"其实是对方的空行），
   胜率也反号。旧注释"to_slow_state 后 turn=who"是错的。
   修复：`slow.turn = who` 显式覆盖后再搜索。

顺带修复：
- `classify_pixel` 青色分支按亮度/饱和分白砖花纹（高亮青 lum 0.78/sat 0.28）与
  蓝砖（深青 lum 0.64/sat 0.58）；`_classify_tile` 白占比阈值 0.45→0.08
  （实测白砖 0.14~0.24、其余全 0.000）。行色 me=[0,4,0,3,4] 全对。
- `state.py` `next_player` 恒 0 → 按 turn 推真实值。
- **真值勘误**：golden1_truth.json 的 left_top/right_top 内容写反（纯目视推导、
  未经像素核对）——蓝白黑黄那摞实测在**右上**盘，左列两盘全空。以图像为准。

验收：golden1 全项 ✓；29 Python 单测 ✓；Rust workspace 全测试 ✓（含墙色位防回归）；
决策健全性（`_tmp_check/adv_sanity.py`）top 建议与行色全一致、0 误报：
行4(已4白) → 「拿白→第5行」补满上墙，行3(已2黑) → 「拿黑→第4行」，
罚分条只剩无处可放的兜底。winrate 98.9（我方大优局面合理）。

教训：**识别读数的"量纲"必须与引擎契约逐字段核对**（像素数 vs 砖数这种量纲错
不会报错、只会静默喂脏数据）；**多来源的同一结构（盘序/墙位）必须用同一份命名
约定**，禁止各层各自脑补顺序；真值 json 也要过像素核对，纯目视推导会带错标签。

## 2026-10-14 关键发现（诊断，推翻两个旧结论）

**E. NNUE 训练管线诊断（train/diag_nnue.py，61.7 万样本）：**
- 标签健康（49/51% 胜负、1.8% 平局）；常数基线 val BCE 0.6931 / **MAE 0.4917**。

- **纠错 1**：旧结论"mae 0.385 停常数基线→结果标签路线瓶颈"是**误读**——0.385 显著优于真基线 0.4917，网络确实学到了。
- **纠错 2**："评估反转/格式 bug"不存在——numpy 按 Rust 布局复现 MAE 0.3946≈torch 0.3915；nnue-d1 60-0 碾压 random；输出分布 std 0.25 不平。

  - d3 vs d2：30-48-2（-80 Elo）——**pathology 仍在**，更强的 hybrid 评估不足以治愈（比 h11 的 -93 略好）。维持"d2 峰值"实用结论。

## 今晚（2026-10-13 通宵）关键发现与真 bug

**A. 已修真 bug（搜索正确性）：**
1. **hash 缺 bag/lid**——不同补砖序列状态哈希冲突，TT 用错值。已补入 bag/lid 打包。【最重要】
2. **终局局面用启发值而非真实胜负**——深层搜不到赢棋，只积累补砖噪声（"越深越弱"主因之一）。已改为 TERMINAL_WIN=1000 真实终局评分。
3. **机会种子用 buffer 下标**——同着法不同排序拿不同种子，TT 不一致。已改为 `chance_seed(pos_key, move_identity)`。
4. debug 下乘法溢出 panic（`wrapping_mul` 已修）。

**B. "深层更弱" search pathology（未解决，核心 blocker）：**
- d3(8-22)<d2、d4(12-28)<d2、d5(3-27)<d3——搜索越深越弱，修完 3 个 bug 仍存在。
- 性质：**Azul 已知 pathology**（随机补袋 + 评估噪声使深层搜索放大噪声选劣着），正是计划 §1.2 设 branching（多补砖聚合）、Rzepecki 用 NNUE 高质量估值要解决的。
- **不是**未发现的实现 bug（h11-d2 碾压随机 30-0 证明引擎核心正确）。
- 剩余方案：branching 聚合 / h11 权重调优 / quiescence。**验证标准：d3>d2 单调。**

**C. NNUE 估值路线（未达标，诚实结论）：**
- 结果标签（Rzepecki 配方）：61.7 万样本（12000 局 h11 自对弈）→ mae 0.385 停常数基线 → vs h11 12-48（20%）、vs h0 3-27。**未达 ≥51%**。

- **关键教训**：Azul 估值的突破点在**搜索随机性处理 + 强教师**，不在标签形式。

**D. 方法论教训（写给未来的自己）：**
1. 改训练配方前**先做 target 分布检查**（std/直方图），并与常数基线对比 mae。

### 2026-10-14 晚 — bug #4（negamax 视角）：搜索真 bug，"深层更弱"治愈
- **发现过程**：写阶段 5 AZ MCTS 时核对 negamax 视角约定，发现终局节点符号可疑；先红后绿回归测试实锤。
- **bug 本质**：`apply()` 在游戏结束时**不翻转 `turn`**（fast.rs L306-308），且补砖后新回合由先手标记持有者开始——**同一玩家可合法连走两手**。但 negamax 无条件取反子节点值：凡"同一玩家继续走"的节点（终局节点 + 回合边界节点），子树符号整体翻转——**搜索把"我赢了"读成 -1000、"我输了"读成 +1000**。与 A 节 hash-bug 级别的真 bug，是 bug 序号 #4。
- **修复**：新增 `child_value(next, parent_turn, ...)` 边界助手——仅当 `next.turn != parent_turn` 时取反并翻转窗口，同视角时直传。见 search.rs。
- **先红后绿验证**：两个回归测试（`search_takes_immediate_win` / `search_avoids_forced_loss`）——临时改回无条件取反时实锤失败（必败局面被读成 +1000、拒绝赢棋着法），恢复修复后全绿。
- **修复后重新标定（release，80 局/对）**：

**教训**：采样框尺寸一旦放大（覆盖花纹），空槽判定就不能信任整框统计——框边必混入邻格。分类特征与判空特征的**感受野要分离**：判空看内区、分类看整块。

## 2026-10-17 公共牌堆"红没读出来"：模板库污染 + dict 撞色覆盖

**症状**：公共牌堆红行整行消失（面板上没有红键），其它行数字看着正常。

**根因**（三层）：
1. **模板库被灰空槽污染**：收割脚本给"行容量内所有格子"都打行色标签，半满行的空槽被标成红/黄——红类 R-B 中位数竟为 0（灰色混入），红黄 margin 被压薄互相误判。
2. **dict 撞色覆盖**：_read_centre 用 {色: N} 存结果，两行被判同色时落败行的键整个消失——红被判成黄后 centre['红'] 不见，而黄被后面的黄行覆盖成正确值，看着"只有红漏了"。
3. **底部位置阈值脆弱**（同族隐患）：标题/按钮排除用"顶 22px / 底 88%"位置阈值，内容整体漂移 12px 时白行被切掉（与首行被 25 阈值误杀同族）。

**修复**：
- 收割：半满行空槽标 EMPTY，只收真砖（红 95→55、黄 37→32，剔除污染样本）。
- 撞色消解：中央牌堆**每色至多一行**是硬规则——两行撞色时留 kNN 距离最小的，落败行在剩余花色里重判（TileBank.predict(allowed=...) 约束最近邻）。
- 行过滤改**间隙列填充**结构判据：真行在图标列与数字列之间(rel x 38..48)是空的（填充≈0.17），标题/按钮横条贯穿整宽（>0.8）——结构特征不随漂移失效，取代两个位置阈值。

**验证**：29 单测 OK；三图全真值 PASS（golden1/红黄截图/本图 centre=蓝2黑1红1黄3白4）；几何漂移矩阵（加顶/下移/宽缩放/内容平移）从 3 处失败降到 0；12 种渲染退化（模糊/gamma/缩放）红行 0 丢失。

**教训**：①模板库的标签噪声比样本量更致命——87 个"红"样本里 40 个是灰空槽，kNN 决策边界直接被拉歪；宁可样本少也要标签干净。②"两行同色→键覆盖→只见丢一行"这类 bug 要靠**领域硬约束**（每色至多一行）消解，而不是调分类阈值。

## 2026-10-17 "个人区域红黄读错"：find_window 盲裁在高 DPI 下毁掉标定

**症状**：用户发截图（含"花园桌游"标题栏）反馈个人区域红黄读错。离线用 read_window 读该图逐格全对（rows/cols/walls/公共牌堆均与像素真值一致），一度无法复现。

**根因**：`find_window` 用蓝底投影夹的是"**纯蓝核心区**"——不含标题栏、右侧公共牌堆白面板、底部罚分条条带。含标题栏的 BASE 标定（golden1 551x1015，标题栏到 y=44）按整窗等比映射，被这个残缺框一裁，x/y 缩放各自错位，个人区域（图像下半）漂移最大 → 红黄互翻。此即 worklog 挂账未修的 "find_window 在 scale≥1.3 触发整列读空" 同一病灶，本次给出确定性复现 + 修复。

**修复**：
1. `read_window` 重裁开关改为**宽高比判据**（`Wd/H > 1.2` 才认为是整屏截图、才用 find_window 定位）；窗口本体（竖版，含标题栏）直接等比缩放读，**不再裁**。

**教训**：①不能在 1x 原图上"逐格核对全对"就断定用户看错——实机抓图是 DPI 缩放后的窗体，必须扫缩放变体复现。②定位切框绝不能只夹"背景色核心"：含边框/侧栏的整体窗口才是标定坐标系，切残 = 标定毁掉。③逐像素阈值兜底（_cell_colour）对缩放敏感，同类问题都会在高 DPI 暴露，砖色识别统一走 kNN 模板匹配。
